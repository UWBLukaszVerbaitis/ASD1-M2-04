1. Cel, odbiorca i zakres

Cel. Aplikacja pozwala zbierać pomysły na życie Filii (dydaktyka, infrastruktura, wydarzenia, samorząd) i pokazać, które mają największe poparcie. Każde miejsce w rankingu wynika z jawnej reguły: liczba głosów malejąco, przy remisie ID rosnąco, a przy wybranym pomyśle widać listę głosów, z których powstała suma.

Odbiorca. Studenci (zgłaszają i popierają pomysły) oraz operator demonstracji — np. przedstawiciel samorządu, który zmienia status pomysłu. Konta i logowanie nie są potrzebne: uczestnik podaje demonstracyjne ID (np. U1), a tryb operatora włącza przełącznik.

Problem. Ręczne zbieranie (kartka, ankieta bez reguł) nie pilnuje zasady „jedna osoba — jeden głos na pomysł”, nie wyjaśnia remisów i miesza liczbę głosów z liczbą osób.

2. Reguły działania i model danych

Reguły

  • Uczestnik może poprzeć kilka różnych pomysłów, ale każdy najwyżej raz (para uczestnik–pomysł jest unikalna).
  • Głos na nieistniejący pomysł jest błędem; wycofanie nieistniejącego głosu niczego nie zmienia (suma nie spada poniżej 0).
  • Usunięcie pomysłu z głosami wymaga potwierdzenia i usuwa jego głosy; przed potwierdzeniem stan się nie zmienia.
  • ID jest niepuste, unikalne i niezmienne: wielkie litery A–Z, cyfry, łącznik, 1–20 znaków. Edycja nie pozwala zmienić ID.
  • Do 1000 pomysłów i 1000 głosów. Każda operacja najpierw waliduje dane, a dopiero potem zmienia stan — odrzucona nie zostawia częściowego zapisu.
  • Ranking: liczba głosów malejąco, następnie ID rosnąco (porównanie kodów znaków: cyfry < „-” < litery). Miejsca są kolejne; remis jest oznaczany („remis z …”).

3. Własne algorytmy i koszt

Wyszukiwanie liniowe pary

findVote(votes, p, i):           // PIERWSZE dopasowanie
  dla k = 0 … m−1:
    sprawdzone++ ; porównania++
    jeśli votes[k].participant ≠ p: dalej
    porównania++
    jeśli votes[k].ideaId = i: zwróć k
  zwróć −1

Szukamy pierwszego dopasowania (para jest unikalna). Klucz złożony porównywany pole po polu — ID pomysłu tylko gdy zgadza się uczestnik. Licznik sprawdzone rośnie raz na rekord, porównania raz na porównanie pola, w tej samej pętli.

Zliczanie głosów

votesForIdea przegląda całą listę głosów i zwraca wszystkie dopasowania — te same rekordy pokazuje karta pomysłu. Dla n pomysłów i m głosów: n·m sprawdzeń. Różni głosujący: lista widzianych ID + wyszukiwanie liniowe.

Sortowanie przez wstawianie

insertionSort(a, cmp):
  dla i = 1 … n−1:
    key = a[i] ; j = i−1
    dopóki j ≥ 0:
      porównania++
      jeśli cmp(a[j], key) > 0:      // a[j] ma stać ZA key
        a[j+1] = a[j] ; j−−          // przesunięcie
      inaczej: przerwij
    a[j+1] = key
cmp(a, b): jeśli a.głosy ≠ b.głosy → b.głosy − a.głosy
           inaczej porównaj a.id z b.id (rosnąco)

Warunek cmp(a[j], key) > 0 oznacza, że a[j] ma stać za kluczem. Przy równości zatrzymujemy się, więc sortowanie jest stabilne. Jedno wywołanie cmp = jedno porównanie klucza (głosy, ID).

4. Technologie i uruchomienie

  • Język: JavaScript (ES2017+), HTML5, CSS3. Brak bibliotek w aplikacji — wyszukiwanie, zliczanie i sortowanie są własnym kodem; z gotowych elementów używane są tylko JSON.parse/stringify, tablice i element <dialog>.
  • Uzasadnienie: działa lokalnie z jednego pliku, bez serwera, kont i płatnego API; ta sama logika (core.js) działa w przeglądarce i w Node, więc testy sprawdzają dokładnie ten kod, który widzi użytkownik.
  • Narzędzia (tylko autor): Node.js ≥ 18 — testy i generowanie dokumentów; Playwright (Chromium) — automatyczny przegląd interfejsu, zrzuty ekranu i eksport PDF.

Uruchomienie aplikacji

  1. Sklonować repozytorium: git clone https://github.com/UWBLukaszVerbaitis/ASD1-M2-04 (lub rozpakować archiwum).
  2. Otworzyć index.html w przeglądarce (Chrome, Firefox, Edge). Nie trzeba niczego instalować.
  3. Startowo ładuje się scenariusz „typowy”; przykład kontrolny — zakładka „Przykład kontrolny”.

Uruchomienie testów

  1. W terminalu: node tests/run.js (lub npm test) — wydruk wejścia, oczekiwanego i uzyskanego wyniku, kod wyjścia 0 przy powodzeniu.
  2. W przeglądarce: zakładka „Testy” → „Uruchom testy”.

5. Architektura i zapis danych

Rys. 2. Moduły i przepływ danych. Linia przerywana — dane zewnętrzne i narzędzia poza aplikacją.

Przepływ jednej operacji

  1. Formularz lub przycisk wywołuje funkcję z core.js (np. addVote), która najpierw sprawdza dane, a zwraca {ok, msg} albo {ok:false, error}.
  2. commit() pokazuje komunikat (✓ albo ✗ z powodem), zwiększa numer stanu i zapisuje stan w localStorage.
  3. render() zawsze wywołuje compute() od nowa: zliczanie, ranking, podsumowania, liczniki. Dzięki temu nie da się pokazać starego rankingu jako nowego — nagłówek rankingu podaje numer stanu, z którego go policzono.

Zapis i odczyt

  • Eksport: exportData → plik skrzynka-pomyslow.json z polami format, version, ideas, votes.
  • Import: parseImport sprawdza cały plik (składnia JSON, format, wersja, typy pól, unikalność ID, istnienie pomysłu dla każdego głosu, powtórzone pary, limity) i buduje nowy stan „na boku”. Dopiero po kliknięciu „Zastąp bieżące dane” stan jest podmieniany. Błędny plik: lista błędów, bieżąca praca bez zmian.
  • localStorage (dodatek): po odświeżeniu strony stan wraca; przy odczycie przechodzi przez ten sam parseImport. Nie zastępuje eksportu.
  • Scenariusze: kontrolny, typowy (8 pomysłów, 16 głosów), graniczny (remisy, ID 1 i 20 znaków, HTML w tekście, tytuł 120 znaków), większy (1000/1000, ziarno 2026), pusty — przyciski w zakładce „Dane JSON” oraz pliki w data/.

Bezpieczeństwo wyświetlania

Wszystkie teksty użytkownika trafiają do strony przez textContent (funkcja el()), nigdy przez innerHTML. Tytuł „<b>Pogrubienie?</b>” ze scenariusza granicznego wyświetla się dosłownie.

Wyjaśnienie wyniku pośredniego (wiersz 6). Przed wycofaniem A i B mają po 2 głosy. 7. Porównanie wyników i liczniki

Sortowanie przez wstawianie vs niezależny wzorzec

Dane generowane powtarzalnie (mulberry32, ziarno 42), ID unikalne. Wzorzec: Array.prototype.sort z tym samym warunkiem — używany tylko do kontroli, nie w głównej ścieżce. Wartości = porównania kluczy.

nuporządkowaneodwróconelosoweremismin n−1maks n(n−1)/2zgodność
109453325945✓ 4/4
10099495025282681994950✓ 4/4
1000999499 500246 675258 825999499 500✓ 4/4

Tabela 4. Wynik własnego sortowania był identyczny ze wzorcem we wszystkich 12 przypadkach.

Interpretacja. Dla danych uporządkowanych każda iteracja kończy się po 1 porównaniu: n−1 (999 dla n = 1000, 0 przesunięć). Dla odwróconych każdy klucz wędruje na początek: n(n−1)/2 (499 500). Dane losowe i remisowe dają około połowy maksimum (246 675 i 258 825), bo średnio połowa par jest odwrócona. Remis głosów nie przyspiesza sortowania — rozstrzyga go ID, więc nadal jest to porządek całkowity. Wniosek praktyczny: po pojedynczym głosie ranking jest „prawie posortowany”, a sortowanie przez wstawianie jest wtedy bliskie liniowemu.

9. Wnioski, ograniczenia i źródła

Wnioski

  • Ranking z jawną regułą (głosy ↓, ID ↑) daje zawsze jednoznaczną kolejność; remis jest widoczny, a nie ukryty.
  • Sortowanie przez wstawianie: 999 porównań dla danych uporządkowanych wobec 499 500 dla odwróconych (n = 1000) — koszt zależy od liczby inwersji, nie tylko od n.
  • Wyszukiwanie liniowe jest najdroższe, gdy wyniku nie ma — a to typowy przypadek przy dodawaniu nowego głosu.
  • Głosów jest więcej niż głosujących, bo głos to para (osoba, pomysł), a jedna osoba może tworzyć kilka par: w przykładzie kontrolnym 3 głosy i 2 osoby, w scenariuszu większym 1000 głosów i 291 osób.

Ograniczenia

  • Zliczanie Θ(n·m) i wyszukiwanie liniowe — wystarczające dla 1000 rekordów, ale nie dla dużych systemów.
  • ID porównywane po kodach znaków: „P-10” < „P-9”; w danych przykładowych stosowane są zera wiodące.
  • Brak kont: ID uczestnika jest deklaratywne (dane demonstracyjne); jeden użytkownik może wpisać cudze ID.
  • Zapis w localStorage jest lokalny dla przeglądarki.

Możliwe rozszerzenia

  • Indeks (mapa) par i licznik głosów aktualizowany przyrostowo — O(1) zamiast O(m); porównanie z obecną wersją.
  • Komentarze do pomysłów, eksport rankingu do CSV, porządek „naturalny” ID.

Źródła

  • Materiały z wykładów i laboratoriów ASD I (wyszukiwanie liniowe, sortowanie przez wstawianie); własny projekt M1 (ASD1-M1-12) — układ projektu i sposób generowania dokumentów.
  • T. H. Cormen i in., Wprowadzenie do algorytmów, rozdz. 2.1–2.2 (sortowanie przez wstawianie, analiza).
  • MDN Web Docs — <dialog>, textContent, File API, localStorage; GitHub Docs — repozytorium i pierwszy commit.
  • Logo i kolorystyka: materiały Filii Uniwersytetu w Białymstoku w Wilnie (szablon pracy dyplomowej).
